Enviando um recurso FHIR

Com o token de acesso em mãos (veja Autenticação), o próximo passo é enviar o registro de saúde. Aqui há uma diferença importante em relação a APIs comuns: o HubSaúde confirma o recebimento na hora, mas processa o conteúdo depois. Seu sistema envia, recebe um comprovante e consulta esse comprovante até o processamento terminar.

1. Padrão assíncrono

Como funciona o envio em duas etapas

O envio é um POST /fhir/{tipo}, ou PUT, PATCH e DELETE em /fhir/{tipo}/{id} para alterar e remover. Quatro cabeçalhos são obrigatórios: Content-Type: application/fhir+json, Accept, Prefer: respond-async e Idempotency-Key. Faltando qualquer um deles, a requisição volta com 400.

Primeiro, o comprovante

A resposta é 202 com corpo vazio, o equivalente a "recebi e vou processar". O cabeçalho Content-Location traz o endereço de uma Task, um recurso FHIR próprio para acompanhar pedidos em andamento (não é o paciente nem o resultado final), e Retry-After sugere quanto esperar antes de consultar.

Depois, o resultado

Consulte com GET o endereço recebido em Content-Location (/Task/{id}) até que Task.status indique conclusão. Em criação, atualização e correção, Task.output.resultReference aponta para o recurso final. Em remoção, o sucesso vem como valueBoolean=true.

Se a rede falhar

Quando você não souber se o envio chegou, reenvie com a mesma Idempotency-Key. O HubSaúde reconhece a repetição, não duplica nada e devolve o mesmo 202, acrescentando Idempotency-Replayed: true quando a operação já terminou.

2. mTLS

Autenticação vinculada a certificado

Se o token foi emitido numa conexão com certificado de cliente, ele carrega o campo cnf e fica atrelado a esse certificado (veja Cache e mTLS). Isso quer dizer que o cabeçalho Authorization: Bearer sozinho não basta: a chamada a /fhir/* também precisa ser mTLS, apresentando o mesmo certificado de cliente usado para obter o token — não precisa ser a mesma conexão TCP, só o mesmo certificado. Caso contrário a resposta é 401, acompanhada de WWW-Authenticate: Bearer error="invalid_token" e de um OperationOutcome explicando a recusa.

4. Teste local

Testando localmente antes de produção

Vale exercitar tudo isso na sua máquina antes de apontar para o ambiente real. O HubSaúde CLI sobe dois ambientes locais, cada um resolvendo um problema diferente.

Simulador: o fluxo completo

hubsaude sim start sobe uma cópia local do HubSaúde em HTTPS na porta 8443, exigindo mTLS como a produção. É onde você testa autenticação e envio de ponta a ponta. Os dados ficam apenas em memória e desaparecem ao reiniciar.

Servidor FHIR: o formato do recurso

hubsaude server start sobe um servidor HAPI FHIR local, sem autenticação, útil para conferir se o recurso está bem formado antes de enviá-lo para produção. Use hubsaude server start --reset para começar do zero.
