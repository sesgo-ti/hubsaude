# Módulo 4: Autenticar

Neste módulo, você entende como o seu sistema comprova a identidade perante o HubSaúde e recebe a autorização para enviar registros. Primeiro, você executa cada passo pelo terminal, para ver o que acontece por dentro. Depois, obtém o mesmo resultado com a biblioteca oficial da sua linguagem.

## Objetivos

Ao final deste módulo, você será capaz de:

- explicar por que o HubSaúde não usa usuário e senha;
- descrever o conteúdo de um `client_assertion` e a sua função;
- obter um token de acesso no Simulador, pelo terminal e pela biblioteca oficial;
- explicar o vínculo entre o token e o certificado do sistema;
- diagnosticar as falhas de autenticação mais comuns.

## Conteúdo

:::info Em poucas palavras

- O HubSaúde **não usa usuário e senha**: o sistema comprova quem é com o **certificado digital**.
- Em troca, recebe um **token de acesso**, uma autorização temporária que acompanha cada envio.
- O token fica **vinculado ao certificado**: não serve a quem não tem a chave privada.
- As **bibliotecas oficiais** cuidam de tudo isso, inclusive da renovação do token.

:::

### Identidade sem senha

O HubSaúde não usa usuário e senha nem chave de API. O sistema comprova a identidade com o **certificado digital** e, em troca, recebe um **token de acesso**, uma autorização temporária que acompanha cada envio. O processo segue o padrão internacional SMART Backend Services, construído sobre o OAuth 2.0.

A obtenção do token acontece em três passos:

<Cartoes>
  <Cartao titulo="1. Descoberta">O sistema consulta o endereço `/.well-known/smart-configuration` e obtém o endereço do servidor de autorização, como visto no módulo 1.</Cartao>
  <Cartao titulo="2. Prova de identidade">O sistema monta um pequeno documento, o `client_assertion`, e o assina com a chave privada. Tecnicamente, é um JWT: um texto em três partes, separadas por ponto, com cabeçalho, conteúdo e assinatura.</Cartao>
  <Cartao titulo="3. Troca pelo token">O sistema envia o `client_assertion` ao servidor de autorização por uma conexão em que também apresenta o próprio certificado. O servidor confere a assinatura e o certificado e devolve o token.</Cartao>
</Cartoes>

### O conteúdo do client_assertion

| Campo | Significado |
| --- | --- |
| `iss` e `sub` | O `client_id` do sistema |
| `aud` | O endereço do servidor de autorização, a quem o documento se destina |
| `iat` e `exp` | O momento da criação e o fim da validade, de poucos minutos |
| `jti` | Um identificador único. O mesmo `client_assertion` não pode ser usado duas vezes |

### Token vinculado ao certificado

O token emitido pelo HubSaúde fica vinculado ao certificado apresentado na conexão, por meio do campo `cnf`.

:::tip Por que isso importa

Todas as chamadas seguintes precisam apresentar o **mesmo certificado** com que o token foi obtido. Assim, um token interceptado não serve a quem não possui a chave privada correspondente.

:::

### Escopos

O sistema pede o token informando os escopos que pretende usar. O servidor concede no máximo o que foi liberado no cadastro. Um escopo não liberado resulta no erro `invalid_scope`.

### Renovação

O token vale por **poucos minutos**. As bibliotecas oficiais guardam o token e pedem um novo automaticamente quando ele está perto de expirar.

:::note Diante de um 401

Se uma chamada for recusada com `401`, descarte o token guardado e peça um novo uma única vez. Se o `401` se repetir, o problema está na credencial, e não na validade do token.

:::

## Prática

Execute os comandos a partir da pasta `curso-hubsaude`, com o Simulador em funcionamento e o sistema cadastrado, conforme o módulo 2. As variáveis criadas nos passos, como `ASSERTION` e `TOKEN`, existem apenas na janela de terminal em que foram criadas.

<Trilha>

<Etapa id="curso-m4-assertion" marcador="1" titulo="Gerar o client_assertion" resumo="Use o assistente do Simulador para criar e assinar a prova de identidade." ambiente="testes">

**O que você faz:** peça ao Simulador que monte e assine o `client_assertion` com a chave de teste.

```bash
ASSERTION=$(curl -s --cacert simulador-server.pem -X POST https://localhost:8443/auth/client-assertion \
  -H 'Content-Type: application/json' \
  -d "$(jq -n --arg chave "$(cat client-key.pem)" '{client_id: "meu-sistema", private_key_pem: $chave}')" \
  | jq -r .client_assertion)
echo "$ASSERTION"
```

:::warning

**Este assistente existe apenas no Simulador e apenas para fins didáticos.** No ambiente oficial, o `client_assertion` é montado pelo seu próprio sistema, normalmente pela biblioteca oficial, e a chave privada nunca é enviada a nenhum servidor.

:::

</Etapa>

<Etapa id="curso-m4-ler" marcador="2" titulo="Ler o conteúdo do client_assertion" resumo="Decodifique o cabeçalho e o conteúdo e identifique cada campo." ambiente="testes">

**O que você faz:** decodifique as duas primeiras partes do documento. Elas não são criptografadas, apenas codificadas.

```bash
echo "$ASSERTION" | jq -R 'split(".")[0] | gsub("-";"+") | gsub("_";"/") | @base64d | fromjson'
echo "$ASSERTION" | jq -R 'split(".")[1] | gsub("-";"+") | gsub("_";"/") | @base64d | fromjson'
```

O cabeçalho informa o algoritmo de assinatura, `RS384`. O conteúdo traz os campos da tabela deste módulo:

```json
{
  "iss": "meu-sistema",
  "sub": "meu-sistema",
  "aud": ["https://localhost:8443/auth/token"],
  "iat": 1793234321,
  "exp": 1793234621,
  "jti": "b39e28bd-17b3-4d44-89f2-b9457bd5e0ad"
}
```

</Etapa>

<Etapa id="curso-m4-token" marcador="3" titulo="Trocar pelo token de acesso" resumo="Envie o client_assertion ao servidor de autorização apresentando o certificado de teste." ambiente="testes">

**O que você faz:** envie o pedido de token. As opções `--cert` e `--key` fazem o curl apresentar o certificado de teste na conexão, e `--cacert` faz o curl confiar no Simulador.

```bash
RESPOSTA=$(curl -s --cacert simulador-server.pem --cert client-cert.pem --key client-key.pem \
  -X POST https://localhost:8443/auth/token \
  -d grant_type=client_credentials \
  -d client_id=meu-sistema \
  -d client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer \
  --data-urlencode "client_assertion=$ASSERTION" \
  -d "scope=system/Patient.c system/Patient.rs system/Task.rs")
TOKEN=$(echo "$RESPOSTA" | jq -r .access_token)
echo "$RESPOSTA" | jq 'del(.access_token)'
```

A resposta informa a validade do token, em segundos, e os escopos concedidos:

```json
{
  "expires_in": 300,
  "scope": "system/Patient.c system/Patient.rs system/Task.rs",
  "token_type": "Bearer"
}
```

O token fica guardado na variável `TOKEN` e será usado no módulo 5. Como ele vale por cinco minutos, repita os passos 1 e 3 sempre que precisar de um novo.

</Etapa>

<Etapa id="curso-m4-vinculo" marcador="4" titulo="Conferir o vínculo com o certificado" resumo="Compare o campo cnf do token com a impressão digital do certificado de teste." ambiente="testes">

**O que você faz:** leia o campo `cnf` do token e calcule a impressão digital do certificado de teste.

```bash
echo "$TOKEN" | jq -R 'split(".")[1] | gsub("-";"+") | gsub("_";"/") | @base64d | fromjson | .cnf'
openssl x509 -in client-cert.pem -outform DER | openssl dgst -sha256 -binary | base64 | tr '+/' '-_' | tr -d '='
```

Os dois valores são iguais. É essa igualdade que o HubSaúde confere em cada chamada: o token só é aceito quando acompanhado do certificado que o originou.

</Etapa>

<Etapa id="curso-m4-erros" marcador="5" titulo="Provocar e diagnosticar falhas" resumo="Repita o pedido em situações de erro e observe as respostas." ambiente="testes">

**O que você faz:** execute cada situação abaixo e compare a resposta com a explicação.

**Reaproveitar o mesmo client_assertion.** Repita o comando do passo 3 sem gerar um novo `client_assertion`. A resposta é `invalid_client` com a mensagem `jti já utilizado`, porque cada documento só pode ser usado uma vez.

**Pedir sem o certificado.** Gere um novo `client_assertion` com o passo 1 e repita o passo 3 sem as opções `--cert` e `--key`. A resposta é `invalid_client` com a mensagem `mTLS client certificate required on this endpoint`.

**Pedir um escopo não liberado.** Gere um novo `client_assertion` e repita o passo 3 com `-d "scope=system/Observation.c"`. A resposta é `invalid_scope`, porque o cadastro não inclui esse escopo.

- Consulte: [Erros comuns da autenticação](../fluxos/autenticacao.mdx#erros-comuns)

</Etapa>

<TabItem value="python" label="Python">

Instale a biblioteca a partir do código-fonte, como descrito na [página do SDK Python](../sdks/autenticacao/python.mdx#instalação), salve o programa como `token.py` e execute-o com `python token.py`.

```python
from hubsaude_client.builder import SmartTokenClientBuilder

client = (
    SmartTokenClientBuilder()
    .fhir_base("https://localhost:8443")
    .client_id("meu-sistema")
    .private_key_pem("client-key.pem")
    .certificate_pem("client-cert.pem")
    .server_trust_anchor("simulador-server.pem")
    .build()
)

token = client.obtain_token("system/Patient.c system/Patient.rs system/Task.rs")
print(token[:40])
client.close()
```

O `jackson-databind` será usado no módulo 5. Salve o programa abaixo como `src/main/java/ObterToken.java`, dentro da pasta `java`, e execute-o com `mvn -q compile exec:java -Dexec.mainClass=ObterToken`.

```java
import br.gov.go.saude.hubsaude.client.SmartTokenClient;

import java.nio.file.Path;

public class ObterToken {

    public static void main(String[] args) throws Exception {
        try (var client = SmartTokenClient.builder()
                .fhirBase("https://localhost:8443")
                .clientId("meu-sistema")
                .privateKeyPem(Path.of("client-key.pem"))
                .certificatePem(Path.of("client-cert.pem"))
                .serverTrustAnchor(Path.of("simulador-server.pem"))
                .build()) {

            String token = client.obtainToken("system/Patient.c system/Patient.rs system/Task.rs");
            System.out.println(token.substring(0, 40));
        }
    }
}
```

## Verificação

**1. Por que o HubSaúde recusa um `client_assertion` já utilizado?**

<Details summary={<summary>Ver resposta</summary>}>

Porque cada documento tem um identificador único, o `jti`. A recusa impede que alguém que tenha interceptado o documento o reutilize para obter um token.

</Details>

**2. Um token foi obtido com sucesso, mas a primeira chamada com ele foi recusada com `401`. Qual é a causa mais provável?**

<Details summary={<summary>Ver resposta</summary>}>

A chamada não apresentou o mesmo certificado usado na obtenção do token. Como o token é vinculado ao certificado pelo campo `cnf`, toda chamada precisa usar a mesma conexão com certificado de cliente.

</Details>

**3. O cadastro do sistema libera `system/Patient.c`. O que acontece se o sistema pedir `system/Patient.c system/Observation.c`?**

<Details summary={<summary>Ver resposta</summary>}>

O pedido é recusado com `invalid_scope`, porque inclui um escopo não liberado. O sistema deve pedir apenas os escopos de que precisa e que foram autorizados.

</Details>

**4. Uma chamada retornou `401` e, depois de descartar o token guardado e obter um novo, retornou `401` novamente. O que fazer?**

<Details summary={<summary>Ver resposta</summary>}>

Interromper as tentativas. O problema não está no token, e sim na credencial: o certificado, a chave ou o `client_id` não correspondem ao cadastro.

</Details>
